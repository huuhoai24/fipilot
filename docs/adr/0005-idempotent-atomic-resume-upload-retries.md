# Make Resume upload retries idempotent and replacements atomic

Each user-initiated Upload Attempt carries an opaque idempotency key scoped to the authenticated user, resume-upload operation, and selected file. The backend records the key and a cryptographic file fingerprint before extraction, prevents concurrent duplicate processing, and distinguishes `processing`, `completed`, `rejected`, and `retryable_failure` outcomes. A repeated key with the same file returns or safely continues the original outcome; the same key with a different file is rejected. Upload and extraction are not automatically retried except for one resubmission after authentication-token refresh. Explicit transient-failure retries reuse the key, while selecting a different file creates a new key.

A Replacement Upload changes the Candidate Profile only after extraction and persistence complete successfully as one atomic operation. Rejected, interrupted, pending, or failed replacements preserve the existing profile and its Interview Readiness. A completed Partial Extraction is a successful replacement with a warning. Interview start may continue from an already-ready saved profile during a pending replacement and snapshots the persisted profile available when the start transaction runs.

Concurrent duplicate requests return `upload_in_progress` while the original is processing and the original response after completion. Reusing a key with another file, operation, or Replacement Upload target returns `idempotency_key_reused`. The UI retains the selected file only in memory for the current page session, never promises recovery across navigation or authentication redirects, and treats `partial_extraction` as a completed upload whose next action is Profile Review.
